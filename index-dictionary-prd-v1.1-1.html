One hook.
One focused mini-book.

Index Dictionary is a sleek, gesture-first reading experience that turns each concept hook into an independent, approximately 10-page visual book. It is built with browser-native HTML, CSS and JavaScript, configured by JSON, and hosted as a static website on GitHub Pages.

1. Purpose & vision

Create a digital library where readers discover a question, open its dedicated book, and understand the idea through carefully sequenced text, vector motion graphics, and graphs—without the distractions of a feed or a conventional web article.

Product principle
The reading page is the hero. The library index is the map. Gestures are the navigation layer. Visuals exist to improve understanding, not to decorate the page.

Objectives

  • Make every concept independently addressable through its own HTML page.
  • Keep the application deployable on GitHub Pages with no server-side runtime.
  • Deliver a stable, full-viewport reading frame below a persistent header.
  • Support a repeatable content model and a single JSON configuration for hooks, dropdowns, and navigation key/value mappings.
  • Provide discoverable, accessible alternatives to touch gestures.

Success indicators

Reading usability

Readers can move between the index, pages, and books without confusion.

Content consistency

Every book follows the same structural contract while choosing visuals appropriate to its topic.

Static deployability

A clean clone of the repository can be published without a build server or secret credentials.

2. Scope & design principles

In scope — v1

  • Home page index.html with library overview, search, category dropdown, hook list, and navigation.
  • Independent HTML file for each hook/book, with shared CSS and JavaScript.
  • Three content page types only: Text, Vector Motion Graphics, and Graph.
  • Cover, internal index, numbered pages, and end page for each mini-book.
  • Touch, pointer, keyboard, and accessible control navigation.
  • Browser-native share, copy-link, bookmark, progress, print, and utility behavior where supported.
  • JSON configuration for books, categories, page metadata, and navigation key/value mappings.
  • GitHub Pages deployment from a repository branch or GitHub Actions.

Out of scope for v1

  • User accounts, server database, cloud-synced bookmarks, collaborative editing, and authoring CMS.
  • Server-side search, personalization, analytics requiring identifiable user profiles, or private content.
  • Arbitrary plugin execution or third-party scripts required for core reading.
  • PDF/EPUB generation as a core requirement; browser print is a utility, not a guaranteed book export.

Experience principles

Focus over chrome

Keep navigation visually quiet; do not cover content with permanent control bars.

One page at a time

Always render a single reading page, including on wide desktop screens.

Progressive enhancement

Core reading and links work even if motion, storage, or sharing APIs are unavailable.

Honest visuals

Label illustrative graphs and cite the source/assumptions for factual data.

4. Content model & book structure

Each hook is a small book with approximately 10 content units. Recommended default: cover + internal index + 7–9 numbered pages + end page. A typical book therefore contains about 10–12 screens including cover and end page. Content may vary when the concept needs fewer or more steps.

Book unitPurposeAllowed page type
CoverTitle, hook question, short subtitle, hero visual.Text with optional vector asset
Internal indexPage list and jump destinations.Text
Numbered pagesTeach the concept in a logical sequence.Text, Vector Motion Graphics, or Graph
End pageKey takeaway, completion state, related hook links, return to library.Text with optional vector asset

Page types

1. Text page

Heading, short sections, definition, example, callout, comparison, or reflection question. Use semantic HTML and readable line lengths.

2. Vector motion graphics page

SVG-based diagram or illustration with optional CSS/JS animation. Include labels, caption, interpretation, and a static reduced-motion state.

3. Graph page

SVG or Canvas plot with axes, units, legend, labels, and explanation. Optional pointer/keyboard inspection; include a text summary and accessible data table when appropriate.

Default learning sequence

  1. Hook question / why it matters
  2. Plain-language definition
  3. Concrete real-life example
  4. Mechanism or system diagram
  5. Graph, comparison, or evidence when relevant
  6. Misconception or opposing perspective
  7. System effects, feedback, or trade-offs
  8. Practical application
  9. Summary and reflection

Do not force every book to contain a graph or motion graphic. Select only the page types that improve understanding. The content inventory may have a target average, but the learning objective controls the final page count.

5. UX, viewport & gesture navigation

Persistent header and reading frame

  • The header remains at the top of the viewport and contains the brand/home link, current book or dropdown navigation, and compact utility access.
  • Below the header, the book page occupies the remaining viewport with a consistent standard margin and a maximum readable content width.
  • Use a viewport-aware frame (e.g. 100dvh with a 100vh fallback), safe-area insets, and responsive padding. Account for mobile browser chrome and on-screen keyboards.
  • Page content must not be clipped. When content exceeds the available height, allow the page body to scroll; do not shrink text to illegible sizes.
  • On desktop, continue to show one page only; do not switch to a two-page spread.

Gesture contract

Gesture / inputActionRules
Swipe left / rightNext / previous pageOnly if the gesture starts in the page navigation surface and exceeds configured distance/velocity thresholds.
Press and hold, then slide horizontallyRapid page browsingPage target follows drag distance; release commits the nearest target. Provide visible progress feedback while holding.
Tap index entryJump to selected pageIndex is a real semantic list of links/buttons, not gesture-only.
Press and slide on index listScrub through entries (optional enhancement)Must not block ordinary scrolling, tap, keyboard, or screen-reader navigation.
Drag on graphInspect data point / cursorGraph owns pointer input inside its bounds; book navigation is suppressed.
Pinch / two-finger pan on visualZoom / pan a complex visual (optional)Only for visuals that benefit from it; provide reset and accessible alternatives.
KeyboardArrow keys / PageUp / PageDown navigate pagesDo not intercept keys while a form control or editable region is active.
Gesture priority rule
Interactions inside a graph or vector canvas belong to that visual. Interactions outside it belong to the book. Browser-native scrolling and text selection take precedence where needed. No essential action may be available only through a gesture.

Motion and transitions

  • Use short, restrained transitions (recommended baseline 180–320 ms); avoid animation that delays reading.
  • Respect prefers-reduced-motion and provide an instant transition mode.
  • Do not animate every SVG element continuously; animate only to reveal a relationship or sequence.
  • Keep the header stable during page changes; animate the page body, not the whole application shell.

8. JSON configuration contract

Use one source of truth for navigation metadata. The home page and book header consume the same JSON. Book content may remain authored in each independent HTML file; the config provides catalog metadata and routes rather than duplicating the full page content.

{
  "schemaVersion": "1.0",
  "site": { "title": "Index Dictionary", "homePath": "./index.html" },
  "navigation": {
    "home": { "label": "Library", "path": "./index.html" },
    "index": { "label": "Book index", "action": "open-book-index" },
    "previous": { "label": "Previous page", "action": "previous-page" },
    "next": { "label": "Next page", "action": "next-page" },
    "share": { "label": "Share", "action": "share-current-page" },
    "bookmark": { "label": "Bookmark", "action": "toggle-bookmark" }
  },
  "categories": [
    { "id": "human-thinking", "label": "Human Nature & Thinking" },
    { "id": "technology-ai", "label": "Technology, AI & Knowledge" }
  ],
  "hooks": [
    {
      "id": "attention-economy", "number": 4,
      "title": "The Attention Economy",
      "question": "Who controls your attention, and who profits from it?",
      "categoryId": "human-thinking",
      "tags": ["attention", "technology", "incentives"],
      "path": "./books/attention-economy.html",
      "pageCount": 10, "status": "published"
    }
  ],
  "gestures": { "swipeThresholdPx": 55, "holdDelayMs": 420, "rapidBrowseEnabled": true }
}

Configuration rules

  • id and path are stable identifiers; avoid deriving paths from display titles at runtime.
  • Every categoryId must reference an existing category, and every published hook path must resolve to a file.
  • Navigation action values must map to an explicit allowlist in JavaScript; never execute arbitrary strings from JSON.
  • Keep the config public and free of secrets. GitHub Pages assets are public.
  • Use a versioned schema and validate it during development or CI.

11. Data, privacy & accessibility

Data model

  • Catalog metadata: public JSON file committed to the repository.
  • Book content: static HTML and local SVG/assets, reviewed through version control.
  • Reader state: optional local storage for bookmarks and last-read page; no cloud sync.
  • Graph data: local arrays or embedded structured data, with source/assumptions in the page.

Privacy and security baseline

  • Never put API keys, credentials, private notes, or user secrets in the public repository or JSON config.
  • Use textContent or safe DOM construction for dynamic labels; avoid injecting untrusted HTML.
  • Open external links safely; use appropriate rel="noopener noreferrer" when opening a new tab.
  • Do not add third-party trackers or social embeds by default.
  • Provide a clear local-data note near bookmark/progress settings.

Accessibility requirements

  • All navigation is usable with keyboard and screen readers; gesture-only navigation is prohibited.
  • Focus order follows the visible reading order; focus is managed after page changes.
  • SVG diagrams include a title/description and a nearby textual explanation.
  • Graphs do not communicate meaning through color alone; include labels, patterns, or textual summaries.
  • Respect browser zoom and text scaling; controls have practical touch target sizes.

12. GitHub Pages deployment

  1. Create a public or appropriately accessible GitHub repository containing the static site files.
  2. Commit index.html, shared CSS/JS, JSON config, each book HTML file, and local assets.
  3. In repository settings, enable GitHub Pages and select deployment from the chosen branch/folder or a GitHub Actions workflow.
  4. Verify the generated URL, including the repository-name path for project sites.
  5. Test direct navigation to at least two book URLs, refresh on a deep link, and return-to-home links.
  6. Run link/config checks before publishing; preview changes in a branch or pull request.
Static hosting limitation
GitHub Pages serves public static files. It does not run JavaScript on the server, protect secrets embedded in files, or provide a database. Every browser request must resolve to a real static file or a supported client-side route strategy.

Assumptions

  • All published books are public and can be served as static files.
  • Content authors are comfortable editing HTML and JSON or using a documented content checklist.

18. v1.1 implementation corrections

This revision tightens the product contract so the design, content model, browser behavior, storage, and static deployment agree. These clarifications supersede ambiguous examples elsewhere in the document.

Primary architecture decision
JSON is the public content catalogue and configuration source. Static HTML/CSS/JS/SVG files are the published book content. Browser storage is for reader-specific state only. A database is not required for v1.

18.1 Resolve content and page-count ambiguity

  • A “page” means one navigable book unit, not a physical paper page or a browser viewport. The default target is approximately 10 navigable units; cover, internal index, numbered learning pages, and end page are included in that target unless a book explicitly documents otherwise.
  • The catalogue's pageCount must equal the number of navigable units in the published book. Do not hard-code a count that disagrees with the actual HTML.
  • Every numbered learning page uses exactly one primary type: text, vector, or graph. Cover, internal index, and end page are structural units and may contain supporting visuals without becoming a fourth page type.
  • Do not force a graph or animation into every book. Use the three approved page types where they improve comprehension.

18.2 Storage contract for a backend-free website

DataSource / storageRule
Book titles, categories, tags, paths, page countsVersion-controlled data/library.jsonPublic, read-only catalogue; validate before publish.
Book text, SVG visuals, graph dataHTML and local JSON/SVG assetsLoad directly from static hosting; no runtime database needed.
Current page and reading progressURL hash + localStorageURL hash is authoritative for a shared deep link; local progress is a fallback when no valid hash exists.
Bookmarks and reader preferenceslocalStorageSmall, simple key/value state; scoped by book ID and versioned key names.
Large offline library, full-text index, or user annotationsIndexedDB, preferably through Dexie.jsOptional future capability; add only when use cases exceed localStorage.

Important: localStorage is not a general-purpose database and is not shared between devices. Browser storage may be cleared or unavailable. Never store secrets, authentication tokens, or private records in a public static app.

18.3 Navigation and state rules

  • On load, resolve a valid URL hash first. If absent or invalid, restore the last-read page for that book; if neither is valid, open the cover.
  • Page changes update the hash using a navigation strategy that supports browser Back/Forward. Choose pushState for intentional page turns or document and test a deliberate alternative; do not silently make all page turns invisible to browser history.
  • Every page has a unique stable ID. Duplicate IDs, missing index targets, and broken book paths fail validation before deployment.
  • Previous/next buttons, index links, keyboard shortcuts, and gestures call the same navigation function so they cannot drift in behavior.
  • At the first and last pages, navigation is bounded and the UI communicates the boundary. It must not wrap unexpectedly.

18.4 Gesture safety and accessibility

  • Use Pointer Events with explicit cancellation on pointer cancellation, loss of capture, or page visibility changes. Clear timers and gesture state on every exit path.
  • Do not navigate when the interaction begins on a link, button, form control, selectable text region, or interactive graph. Preserve normal vertical scrolling and browser text selection.
  • Hold-and-slide browsing is an enhancement, not a required path. Show a visible target preview and commit only on release; cancel cleanly when the pointer leaves the navigation surface or the user cancels.
  • Provide visible focus indicators, semantic buttons/links, meaningful accessible names, and an announced page title/counter. Do not rely on color or gesture alone.
  • Honor prefers-reduced-motion; avoid forced animation and support a reader setting to disable gesture navigation.

18.5 Visual direction and responsive layout

  • Use a single-page reading canvas on desktop, tablet, and mobile. Do not introduce a two-page spread.
  • The page frame must fit below the fixed header with standard outer margins, safe-area insets, and a 100dvh layout with a sensible fallback. Content that exceeds the frame scrolls inside the page; it is never clipped or reduced below readable size.
  • Support both light paper and dark/black visual treatments as book-level design tokens. A dark page is a valid art direction, not a global requirement; contrast and readable text remain mandatory.
  • Use a consistent content grid, type scale, spacing scale, and page footer. Motion should explain a process or relationship rather than decorate empty space.
  • Graphs must distinguish measured data from conceptual illustrations. Include units, labels, source/method notes, and a concise text interpretation; if there are no real data, label the graph “illustrative” prominently.

18.6 Content security and resilience

  • Render author-controlled text as text, not by interpolating untrusted strings into innerHTML. If rich HTML is required, sanitize it or use a constrained authored template.
  • Configuration action names are mapped through a fixed allowlist; never execute a function or JavaScript expression supplied by JSON.
  • Feature-detect Clipboard, Web Share, storage, and Pointer Events. Each unavailable API has a usable fallback and a clear user-facing result.
  • Show a helpful error state if catalogue JSON fails to load or a book is missing. Keep a usable home link and recovery action; never leave a blank black/white screen without explanation.
  • Use relative asset paths that work under GitHub Pages project subpaths. Test direct navigation to a book URL, refresh on a page hash, and shared deep links.

18.7 Release gates

GatePass condition
Catalogue integrityAll IDs/slugs unique; categories exist; published paths resolve; page counts match.
NavigationCover, index, first/middle/last pages, deep links, refresh, Back/Forward, and direct book URLs work.
Gesture regressionSwipe turns pages; vertical scroll, text selection, index taps, and graph interactions do not accidentally turn pages.
Storage resilienceProgress/bookmarks work locally when storage is available and degrade gracefully when disabled or cleared.
Responsive/accessibilityTest narrow mobile, tablet, and desktop widths; keyboard-only use; focus states; reduced motion; contrast; and screen-reader labels.
Static deploymentClean repository deploys without secrets, backend, build step, or mandatory third-party runtime dependencies.
Visual integrityNo clipped text or blank pages; all diagrams have labels/alt descriptions; conceptual graphs are clearly marked.
Recommended delivery order
1) Make one book and the library work with shared navigation and JSON metadata. 2) Validate URLs, page IDs, accessibility, and responsive layout. 3) Add local bookmarks/progress. 4) Add optional IndexedDB/offline search only when required. 5) Publish to GitHub Pages and test the deployed site, not only local file previews.
