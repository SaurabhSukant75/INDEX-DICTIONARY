Index Dictionary is a focused digital library for discovering short visual books, reading them, organizing a personal catalog, importing standalone HTML books, and continuing where you left off. The shared catalog is curated by editors; personal books and reading history stay on the reader’s device.

1. Product direction

The product is a book library and reader first. Discovery, personal organization, safe HTML import, and reading continuity are the core jobs—not gestures or a particular visual effect.

Product promise
Find a useful book, read it without distraction, and return to it later—whether it came from the shared catalog or the reader’s own HTML file.

What changed from v1.1

  • Added reader-owned HTML imports and a personal library alongside the public catalog.
  • Added editor-only publishing for shared catalog books; ordinary readers cannot publish directly to everyone.
  • Made reading history, bookmarks, and progress first-class product requirements, stored locally in v1.
  • Defined a dedicated no-results page/state instead of silently opening an unrelated/default book.
  • Reprioritized swipe and animation as enhancements; accessible controls and reading remain primary.
  • Replaced the “no backend” assumption with a hybrid model: static public reading plus a protected editorial publishing capability.

Product outcomes

Find

Readers can search and browse a growing collection and understand when there are no matches.

Read

A book opens directly, reads well on phone and desktop, and supports accessible navigation.

Organize

Readers can save books, group them into personal collections, and find recent or unfinished reading.

Contribute safely

Readers import private HTML books; authorized editors curate and publish books to the shared catalog.

2. Scope, roles, and principles

In scope for v1

  • Browse, search, filter, and open books in a public catalog.
  • A personal library combining saved public books and locally imported HTML books.
  • Personal collections, bookmarks, reading history, last-read position, and completion state.
  • Three connected catalog structures: hierarchical topic taxonomy, concept knowledge graph, and editor-curated ordered learning paths.
  • Import, preview, rename, organize, and remove standalone .html/.htm books.
  • Editor-authenticated metadata entry and publication for shared books; book HTML is added manually under book/ and deployed from the repository.
  • Independent book URLs, internal contents, stable page links, and return-to-library navigation.
  • Static public book files and reader experience; protected catalog metadata service for editors; repository-controlled file deployment.

Roles and access

RoleCan doCannot do
ReaderBrowse and read public books; import HTML to their private device library; save, organize, bookmark, and track progress.Publish to the shared catalog or access another reader’s private library.
Editor / maintainerEnter catalog metadata through an authenticated service; add HTML manually under book/ in a reviewed repository change; validate, deploy, publish, update, or unpublish the catalog entry.Publish metadata before the referenced deployed file is verified or bypass the content policy.

Out of scope for v1

  • Reader accounts, cross-device synchronization, social profiles, comments, and shared personal collections.
  • PDF/EPUB import, arbitrary ZIP uploads, a general-purpose authoring CMS, or collaborative editing.
  • Personalized recommendations or behavioral analytics.
  • Automatic public publishing by readers.
Privacy boundary
Reader uploads, personal collections, and reading history are private to that browser in v1. Shared publication is a separate editor action and must be explicit.

4. Core user journeys

Discover a shared book

  1. Open the library and browse categories or enter a search query.
  2. Review matching book cards with title, short description, category, and reading status where relevant.
  3. Open a result; use the book contents or next/previous controls to read.
  4. If there are no matches, show a dedicated “No books found” page/state in the library with clear-search and browse-all actions.

Organize and continue reading

  1. Save a shared book or import a personal HTML book.
  2. Add either book to a personal collection; collections and saved state remain local to the device.
  3. Reading updates last-read position and recent history. The reader can bookmark a page or mark a book complete.
  4. Open Continue reading or History to return to the most recent position; a valid shared page link takes precedence over saved progress.

Import a personal HTML book

  1. Select a local .html or .htm file from the device.
  2. The app validates the file, extracts a suggested title, asks for any missing catalog metadata, and displays a preview.
  3. Confirming import stores the book and its metadata in browser-local storage; no upload to the shared catalog occurs.
  4. The imported book appears in My Library and can be renamed, organized, read, or removed.

Publish to the shared catalog

  1. An authorized editor enters title, description, taxonomy, concepts, tags, and source/credit details in the catalog metadata form. The form does not accept an HTML file.
  2. The catalog service creates a draft and returns a generated book ID and expected book/ path.
  3. A maintainer manually adds the self-contained HTML file at that path in a reviewed repository change.
  4. CI validates the path, file, size, and content policy, computes the file hash, and deploys the book with the site.
  5. After deployment verification, the editor explicitly publishes the catalog entry. Updates add a new file revision and redeploy; the editor can unpublish the metadata entry.

6. Book and catalog model

A book is an independently readable HTML document. The “Attention Economy” sample demonstrates the intended short, visual reading experience: a cover, an internal index, sequenced explanations, diagrams, an illustrative graph, and an ending. It is a content example, not a requirement that every book copy its exact length, theme, or gestures.

Catalog design: three complementary structures

Taxonomy, knowledge graph, and learning sequence are separate catalog structures. A category tells readers where a book belongs; a concept graph tells readers what ideas relate; a learning path tells readers what order to follow. Do not use a graph edge or category sort order as an implicit curriculum.

Content principles

  • Use short sections, clear headings, concrete examples, and a logical beginning-to-end learning path.
  • Text, diagrams, SVG/vector visuals, and graphs are supported when they improve understanding; no book is required to use every type.
  • Factual claims and measured graphs include a source and context; conceptual or invented data is prominently labelled illustrative.
  • Every book remains readable when animation or optional browser APIs are unavailable.

7. Architecture and data boundaries

The MVP uses a book/ module for HTML files and a catalog database for metadata and hashes only. The HTML book body is never stored in the database or submitted to the catalog service. The editor form updates catalog metadata only; a maintainer adds the file to the repository manually, then CI validates and deploys it. GitHub Pages cannot accept runtime uploads.

AreaRecommended product boundaryPersistence
Book contentVersioned HTML files manually added to the book/ module and deployed from the repository.Version-controlled static files; no HTML body in the catalog database or metadata service.
Catalog metadataRelational records for stable book ID, title, normalized title/hash, category, tags, status, and content revision/hash.Database stores metadata and hashes; title hash is an exact-lookup aid, not an ID or full-text search index.
Reader library and historyBrowser-side storage for imported HTML, personal collections, bookmarks, and progress.IndexedDB; local to the current browser/device in v1, without reader accounts or sync.
Catalog metadataAuthenticated editor workflow creates/updates draft metadata and points to the expected repository file path.Metadata service/database only; CI checks that the manually committed file exists and matches before the entry can be published.
State precedence
For a public book, a valid page in the URL opens first. Otherwise offer the saved reading position, with an explicit option to restart. Local reader state must never be written into the public catalog.

Anonymous reading and personal data do not require reader accounts. A protected metadata API and editor identity are required for shared-catalog changes. See the MVP architecture and technical decisions for routes, project folders, catalog and IndexedDB schemas, HTML rendering/isolation, and the metadata-only/manual-file deployment workflow.

8. Privacy and safe HTML handling

  • Explain before import that a personal book is stored in this browser and is not shared or synchronized. Explain that clearing browser data may remove it.
  • Provide clear local-data deletion controls. Do not collect reader history or upload personal files for analytics.
  • Treat imported HTML as active, untrusted content. Never render it with unrestricted access to the parent application, its storage, or its authentication context.
  • Preview and read imported content in an isolated, restrictive context; disallow or constrain external scripts, network access, forms, downloads, and top-level navigation according to a documented content policy.
  • Validate file type and size, handle malformed documents safely, and show a clear rejection reason. A file extension alone is not proof that content is safe.
  • For shared books, enforce editor authorization on catalog metadata/publication changes, validate repository files in CI, preserve an audit trail of publish/unpublish actions, and keep secrets out of public files.
  • Shared publication is explicit and may expose the book publicly. Show that consequence before the editor publishes.
Security product decision
The sample book includes inline JavaScript for navigation. Supporting active HTML safely needs an isolated rendering policy that preserves approved book behavior without granting the file access to the host app or reader data. The import experience must not silently execute arbitrary uploaded content with the app’s privileges.

10. Success measures

Use privacy-respecting usability tests and release checks before adding product analytics. Proposed initial validation goals (hypotheses to verify with representative readers):

  • At least 4 of 5 test participants find and open a requested book within one minute using search or categories.
  • At least 4 of 5 participants correctly recover from a no-results search without assistance.
  • At least 4 of 5 participants import a supported HTML file and find it in My Library without help.
  • At least 4 of 5 participants can resume a previously opened book and identify their saved progress.
  • All release acceptance checks for editor authorization, local-only reader data, keyboard navigation, and safe import pass.

These are usability test targets, not a request to collect individual browsing behavior. Any future analytics requires a separate privacy and consent decision.
